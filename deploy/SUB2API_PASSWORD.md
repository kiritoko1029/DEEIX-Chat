# 使用 sub2api 邮箱密码登录 Chat

从 `2026.11.13` 起，Web 登录页可直接使用 **sub2api 的邮箱和当前密码**。这是远端验证，不是密码复制或数据库共享。

- Chat 将本次输入交给配置的可信 sub2api 验证，不保存该密码。
- 验证通过后按“实例地址 + 远端用户 ID”复用已有 Chat 账号。之前通过免登录链接创建的聊天记录、模型服务和账号关联不变。
- sub2api 修改密码后，下一次通过这个入口登录必须使用新密码。
- “Chat 本地账号／管理员”是独立入口，不会在远端失败后自动尝试本地密码，也不会按相同邮箱合并账户。

**无需把 Chat 的内部用户名改成邮箱，也无需删除或重新注册账号。**

## 启用

先升级到包含此功能的镜像，再在实际挂载的配置文件中增加开关：

```yaml
sub2api:
  enabled: true
  password_login_enabled: true
  base_url: "https://sub2api.example.com"
  api_base_url: ""
  allow_embedding: false
```

上面的域名是示例。**已有接入请保留原 `base_url`、网关和嵌入设置，只增加 `password_login_enabled: true`。** 实例地址参与身份关联，不要为了开启密码登录随意换域名或别名。

对应环境变量为 `SUB2API_PASSWORD_LOGIN_ENABLED=true`；环境变量优先于 YAML。默认关闭。还需开启原 sub2api 接入及 Chat 管理后台的个人模型服务。本地 sidecar 模式不提供此功能。

只修改配置文件后重启应用；若修改了 Compose 环境变量或挂载，应重新创建应用容器。保持原数据库、存储卷和加密密钥，不要运行 `down -v`。

## 登录流程

1. 在 Chat Web 登录页选择 **sub2api 账号登录**。
2. 输入 sub2api 邮箱和密码。
3. 如果源站开启 Turnstile，在当前页面正常完成验证；未开启时不显示验证码。
4. 如果源站为该用户要求 TOTP，再输入 **sub2api 的六位验证码**。
5. 若 Key 的协议无法确定，选择 Responses、Messages、Chat Completions 或本次跳过。选择仍需通过原有归属、状态、额度和模型列表检查。
6. 若关联的 Chat 账号也启用了二次验证，继续完成 **Chat 的二次验证**。两种验证不能相互替代。

仍沿用现有接入成功条件：至少一个个人模型服务可用。密码正确但没有可用 Key、达到服务上限、模型列表探测失败时，仍可能无法完成接入，并显示具体导入摘要；这不等于密码错误。

读取模型列表不是收费推理探测，也不保证每种生成接口均可用。

## 验证码与浏览器要求

能力来自配置的 **当前 sub2api 实例**，不是 Chat 本地注册验证码设置。不同源站的设置可以不同；不要根据另一域名的配置推断当前实例。

首期支持 `none` 与 Cloudflare Turnstile，以及远端 TOTP：

- 源站关闭验证码时，直接验证邮箱密码。
- 源站开启 Turnstile 时，使用源站公开 sitekey，Chat 不需要其 secret；但 Cloudflare widget 必须授权 **Chat hostname**。
- 不支持的验证码提供方、配置冲突、缺失配置或需要额外登录协议同意时，入口会明确不可用，并引导前往 sub2api。
- 不会伪造 Origin/hostname、搬运验证码、反代挑战页或关闭源站验证来绕过限制。

本入口首期为 **Web-only**；桌面应用保留原有登录方式。建议以 HTTPS 顶层页面或新窗口登录。跨站 iframe 和浏览器 Cookie 策略可能阻止流程绑定 Cookie；不能通过关闭 Cookie 绑定绕过，遇到此情况请在新窗口打开 Chat。

## 临时状态、限流与多实例

- 密码与 TOTP 仅用于当前请求，不进入数据库、缓存、登录 flow 或日志。
- 远端临时 token/access token 只在服务端有界内存中保留；浏览器仅在内存中持有 Chat 的 opaque flow ID，不接收远端 token。
- flow 总有效期最多五分钟，重试不延期；绑定 HttpOnly、SameSite=Strict Cookie 及客户端 IP/UA，取消或结束时清理。
- 单进程最多 1024 个 flow。重启会让未完成流程失效。多副本部署必须使用粘性路由；没有默认把凭据写入 Redis 或数据库。
- 新入口始终受 IP 限流保护，即使关闭通用公开认证限流也不会关闭这一层；另有邮箱 HMAC、实例出站和 flow 重试限制。当前邮箱每分钟 5 次、实例认证操作每分钟 18 次，远端 TOTP 最多尝试 5 次。
- 多个用户会共享 Chat 后端的出站 IP，可能共同触发源站限流。尊重 429 和 Retry-After，不自动重发密码请求、不切换出口或伪造 IP 绕过。

## 身份、安全与会话边界

账号只按可信实例和远端 ID 关联。远端邮箱是展示资料，不自动成为本地已验证邮箱；远端 admin 角色不会自动赋予 Chat 管理员权限。

登录、远端 2FA 和后续身份读取使用固定出站 User-Agent `DEEIX-Chat-Sub2API/1.0`。源站开启 session binding 时，出站 IP 也需保持稳定。实例或网关配置发生变化会使旧流程失效，不使用旧流程凭据访问新目标。

收到远端 refresh token 后，仅尽力注销这一次返回的单个 refresh token，不调用 refresh 或全会话撤销。上游注销接口可能吞掉存储删除错误，故**无法保证远端绝不留下 refresh session**；异常断网或进程终止也可能导致无法回收。

**Chat 现有会话仍有自己的生命周期。** 修改 sub2api 密码会影响后续密码验证，但不会自动撤销已经签发的 Chat 会话；需要时在 Chat 的会话管理中退出。此功能不是跨站单点注销。

原有 Key 配额、至少一个可用服务、SSRF、同源校验、个人服务停用状态及本地 2FA 同步限制继续适用，参见 [sub2api 接入说明](<SUB2API.md>)。不要在反向代理、APM 或调试日志中记录认证请求体。
